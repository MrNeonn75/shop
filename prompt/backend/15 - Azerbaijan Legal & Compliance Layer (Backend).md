
GOAL: Build module `compliance` and wire Azerbaijani legal requirements into the system through VERSIONED, EFFECTIVE-DATED, SOURCE-REFERENCED RULE PACKS.

NON-NEGOTIABLE PRINCIPLES
1) Law is DATA, not code. No legal rate, threshold, deadline, or entitlement is hardcoded in business logic. Everything lives in rule packs with effective dates, so legislative changes (Azerbaijani tax and labor law changed in 2026 and continues to change) need no deployment.
2) Every rule has: id, jurisdiction=AZ, domain, title (az), parameters (typed JSON schema), effective_from/effective_to, legal_reference (act name, number, article), source_url, source_type (OFFICIAL / SECONDARY), status (UNVERIFIED, VERIFIED, SUPERSEDED, DISPUTED), verified_by (name + role: accountant/lawyer), verified_at, notes, version. History is append-only.
3) Seeded rule values below are REFERENCE VALUES collected from secondary sources and are marked UNVERIFIED. In production (ENV=production), a rule pack with any UNVERIFIED rule cannot be ACTIVATED for: fiscal receipts, tax calculation on documents, payroll finalization, and consent/privacy enforcement. Activation requires a VERIFIED status set by a user with compliance.rules.verify (two-person rule: verifier ≠ editor), with evidence attachment. In non-production environments UNVERIFIED packs may be used with a visible banner. Never present the system as "legally compliant"; it supports compliance and shows verification status.
4) Conflicting sources are recorded as DISPUTED with both values and sources; the system picks neither until a verifier resolves it.
5) The system never submits anything to a government system on its own unless a verified integration exists; it produces DRAFT data files and checklists for the accountant.

1) COMPLIANCE FRAMEWORK
- Tables: legal_rules, rule_packs (bundles per domain: tax_vat, fiscal_receipt, payroll_tax, payroll_social, labor_time, labor_leave, consumer_returns, personal_data, retention), rule_pack_versions, rule_verifications (evidence files), obligations (recurring duties with owner, cadence, next_due, status — deadlines are DATA entered/verified by accountant, none hardcoded), compliance_events (append-only log).

- Endpoints: list/filter rules, rule detail with history, propose change (draft), verify/reject with evidence, activate with effective date, diff between versions, export register as CSV/PDF, compliance status summary (per domain: ACTIVE-VERIFIED / ACTIVE-UNVERIFIED(non-prod) / MISSING), obligations calendar CRUD with reminders via notifications (B13).
- Startup/health: /health/details reports compliance status; in production, missing/unverified mandatory packs raise critical notifications and block the dependent features (feature gates return COMPLIANCE_RULES_NOT_VERIFIED with the missing domain list).

2) TAX — VAT (ƏDV) AND TURNOVER MONITORING
Reference seed (UNVERIFIED):
- VAT standard rate 18% (single rate; Tax Code art. 173). Retail prices are VAT-INCLUSIVE; price display, receipts, and reports must compute net/VAT split by the rule: vat = gross × rate / (1 + rate) with central rounding rules; line-level and receipt-level rounding policy configurable and tested so sums match exactly.
- Tax classes (via B3 settings) map to rule parameters: STANDARD (18%), EXEMPT, ZERO, SIMPLIFIED_TAX_PAYER (taxpayer regime flag at company level: VAT payer / simplified-tax payer / other). Company tax regime and VÖEN stored in company profile with effective dating.
- VAT registration threshold monitoring: reference 200,000 AZN annual turnover; for retail sales to unregistered buyers, cashless (POS terminal) receipts count with coefficient 0.5 toward the threshold (reference: Tax Code art. 155.1-1). Implement a `turnover_monitor` read model: rolling 12-month and calendar-year turnover by tender with the coefficient rule from the rule pack, projection and alert events (80%, 95%, 100%) to notifications. Mark all as indicative, not a filing.
- ƏDV invoices (e-qaimə/e-VHF) for B2B and B2G supplies are produced in the Electronic Tax Office, not by this system: provide a `TaxInvoicePort` (NOT_CONFIGURED) and a DRAFT export of the data an accountant needs (buyer VÖEN, items, VAT) plus a reconciliation table linking ERP invoices to externally issued e-qaimə numbers (manual entry/import). No automatic submission.
- Purchase side: record supplier e-qaimə number, VAT amount, and VAT-deductibility flag on supplier invoices (B6) as data fields; VAT payable/receivable summary report (draft) for the accountant.
- Tax report data pack (monthly/quarterly/annual): sales by tax class, net/VAT, returns, purchases VAT, with source drill-down; exports labeled DRAFT FOR ACCOUNTANT REVIEW.

3) FISCAL RECEIPTS — E-KASSA (extends B7/B8/B13)
Reference facts (UNVERIFIED, verify against current Tax Code and State Tax Service/Ministry of Taxes rules): retail cash settlements must go through a cash register (e-kassa: software cash register + control mechanism device) connected in real time to the state information system (Tax Code art. 16.1.8); approved e-kassa operators are listed on the official e-kassa portal; the fiscal receipt carries mandatory data and a QR code.
- Implement `FiscalService` port (extend B7 scaffold) with provider-agnostic operations: open_shift, create_receipt (sale), create_return_receipt (linked to original fiscal receipt), advance receipt (if needed), cash_in/out records, x_report/z_report/close_shift, get_status, reprint/copy, cancel where allowed. Concrete adapters are written ONLY after the business selects an approved e-kassa operator/device and receives its technical documentation; until then status = NOT_CONFIGURED and NO adapter is invented.
- Company setting `compliance.fiscal.mode`: REQUIRED (default in production for retail), OPTIONAL (dev/staging/demo). In REQUIRED mode a sale or return is NOT completed unless a fiscal receipt is obtained. Define and test the transaction design: (a) PREPARE: reserve receipt number and stock inside DB transaction as PENDING_FISCAL, (b) call fiscal adapter (outside DB transaction, with timeout and idempotency key), (c) on success store fiscal data (fiscal ID, receipt no, QR payload, device serial, timestamp, control-mechanism registration no) and COMMIT sale as COMPLETED, (d) on definite failure roll back with exact reasons, (e) on UNKNOWN outcome (timeout) put sale in FISCAL_UNKNOWN and resolve via reconciliation job/manual resolution by querying the operator — NEVER silently retry creating a second fiscal receipt, NEVER mark paid without confirmation. Document the state machine and failure matrix; reuse B7 payment_attempts patterns.
- Fiscal data stored on sale/return records (immutable): fiscal_receipt_id, fiscal_number, qr_payload, device_serial, fiscal_mode flag, issued_at, check_type (sale/return/advance), provider, raw response (redacted).
- Receipt content validation: receipt template (B3) gets a compliance check that every mandatory element in the active fiscal rule pack is present — reference list to seed as UNVERIFIED: taxpayer name, VÖEN, date and time, outlet name + tax-office registration code + address, per-line item name/unit/quantity/unit price/total including VAT rate and amount (or simplified-tax rate), receipt number within the shift, cash register make and serial number, fiscal-mode mark, QR code, amount paid, advance amount (if advance), change returned, outstanding amount (credit sale), payment form (cash, cashless, bonus, gift card), receipt type (sale/return), control-mechanism registration number. If the official list differs, the rule pack is edited — not the code.
- Returns: B8 return completion creates a fiscal RETURN receipt linked to the original; refund tender rules respect fiscal data; return without original fiscal receipt requires explicit compliance reason code and is flagged for accountant review.
- Non-cash tenders must be consistent between the POS terminal slip, fiscal receipt, and ERP payments; reconciliation report fiscal-vs-ERP totals per shift/day (differences raise alerts).
- Gift card / bonus tenders recorded with their own tender types because the fiscal receipt distinguishes them.
- Offline/failure policy: no offline selling is claimed. If the fiscal service is down in REQUIRED mode, POS shows FISCAL_UNAVAILABLE and blocks finalization; any documented legal fallback (e.g. temporary procedures) must be added by the business as a rule pack + explicit procedure after legal confirmation.
- Fiscal shift sync: B7 register shift open/close triggers fiscal shift open/close; Z-report data stored and reconciled with ERP shift totals.

4) PAYROLL TAX AND SOCIAL CONTRIBUTIONS (extends B10; replaces "empty rule sets")
Reference rule-pack seed for private non-oil/gas sector 2026 — ALL UNVERIFIED, effective-dated, with DISPUTED markers where sources conflict:
- Minimum monthly wage: 400 AZN (validation: salary profiles below it are blocked/flagged unless part-time proration applies).
- Personal income tax (transitional 2026 schedule, reference): 3% on monthly income up to 2,500; 75 + 10% of the excess over 2,500 up to 8,000; 625 + 14% above 8,000. Sources indicate the transitional rates change from 1 Jan 2027 and a later rate path — DO NOT seed 2027+ values; require a new verified pack before the effective date and raise an obligations reminder 60 days earlier.
- Mandatory state social insurance (DSMF/SSPF) reference: employee 3% on the first 200, then 6 + 10% above 200; employer 22% on the first 200 (shown as 44 on the first 200 in some sources and 2%/15% structure in others → mark DISPUTED), then 15% above; reduced employer rate (reference 11%) on the portion above 8,000 — DISPUTED detail; sector differences (oil & gas, public sector) are OUT OF SCOPE and the pack is flagged `sector=private_non_oil`.
- Unemployment insurance reference: 0.5% employee + 0.5% employer on salary.
- Mandatory medical insurance reference: 2% employee + 2% employer up to a threshold, 0.5% + 0.5% above (threshold reported as 2,500 by some sources and 8,000 by others → DISPUTED; no default activated).
- Rule engine (extends B10): bracket/threshold/cap definitions with `base` selection (gross, taxable base after contributions if the rule says so — the order of deductions and the taxable base for income tax are RULE PARAMETERS to be verified, not code assumptions), per-employee flags (e.g. preferential categories, disability status handled WITHOUT storing diagnoses — only a generic `tax_preference_code` selected from a verified list), monthly cumulative vs period-based computation mode, rounding rules.
- Outputs: payslip lines reference rule ids/versions; payroll run snapshot stores the pack version; DRAFT data export for the monthly unified employer declaration/DSMF reporting for the accountant (columns configurable); NO automatic submission to tax/DSMF systems.
- Payroll finalization in production is blocked unless all payroll packs used are VERIFIED (feature gate from the framework).
- Golden tests are parameterized FROM THE RULE PACK in the test fixture (not hardcoded numbers in test code); include worked examples marked as "illustrative, unverified" in docs.

5) LABOR LAW — WORKING TIME, OVERTIME, LEAVE, CALENDAR (extends B10)
Reference seed (UNVERIFIED; Labor Code amendments took effect 16 Jan 2026 — verify article numbers against the current consolidated text on the official legal portal):
- Normal working time: max 8 hours/day and 40 hours/week; reduced norms for specified categories (e.g. 36-hour for harmful conditions) as selectable work-time regimes; six-day week allows max 7 hours/day (40-hour week), shorter pre-day-off limits; shifts under cumulative accounting capped at 12 hours (reference); pre-holiday day shortened by 1 hour per the official production calendar.
- Night work: 22:00–06:00 (reference) — attendance engine flags night hours; night supplement is a rule parameter (not seeded).
- Overtime: employee consent and documentation required; reference minimum pay multiplier 2× the regular hourly rate for time-based pay (Labor Code art. 165); reference limits from secondary sources (4 hours over two consecutive days, 120 hours/year) are DISPUTED/UNVERIFIED. Attendance/payroll validation warns or blocks per rule `enforcement=warn|block`.
- Work on public holidays/rest days: pay multiplier as rule parameter (reference 2×, UNVERIFIED).
- Annual leave: minimum 21 calendar days (Labor Code art. 114; constitutional guarantee); reference 30 days minimum for managerial/specialist (white-collar) employees (UNVERIFIED, depends on classification → needs verified job-category mapping); additional leaves (seniority, hazardous work, special merit lists) as selectable leave rule types; leave pay and unused-leave compensation on termination calculated per rule parameters (verify the averaging method — rule data); accrual by working year, schedule-based leave assignment, carry-over rules as data.
- Salary payment frequency: reference "at least twice a month, interval ≤ 16 days" from a secondary source (UNVERIFIED) → implement as a validation warning on payroll schedules driven by the rule.
- Production calendar: annual calendar import (holidays, shortened days, transferred days; Cabinet decisions determine Nowruz/Ramadan/Gurban days each year; reference 2026: 241 working days and 1,922 working hours on a 5-day, 40-hour week). Provide `calendar_years` import (CSV/JSON) with source reference and verification; B10 schedules/attendance/leave/payroll use it. No holiday is hardcoded.
- Employment contract content checklist (rule data): labor function, working conditions (time/rest, wages and supplements, annual leave, safety, mandatory social/other insurance), probation (counts actual working time) — contract builder validates required fields; registration of employment contracts in the state system (if required) tracked as an obligation/status field with manual confirmation until an integration exists (NOT_CONFIGURED).
- Compliance reports for HR: overtime hours vs limits, hours per day/week violations, rest-day work, unpaid/ underpaid indicators, leave entitlements vs balances.

6) CONSUMER PROTECTION — RETURNS AND EXCHANGES (extends B8)
Reference seed (UNVERIFIED; Law "On Protection of Consumer Rights" No. 1113 of 19 Sept 1995):
- Non-food goods of proper quality that do not suit the consumer by shape, size, style, color or similar may be exchanged for a suitable item within 14 days, NOT counting the purchase day, provided the item is unused, appearance/consumer properties, seals/labels are preserved, and proof of purchase exists. If no suitable item is available for exchange, the consumer may return it and receive the money paid.
- Goods on the Cabinet of Ministers' list of non-returnable/non-exchangeable proper-quality non-food items are excluded (a secondary source cites Cabinet Decision No. 114 — VERIFY the current list). Implement `legal_returnability` per category/product flag (RETURNABLE / NON_RETURNABLE_BY_LAW / CONDITIONAL) populated from the verified list, e.g. category-level mapping with accountant/lawyer review; footwear and clothing default to RETURNABLE (reference).
- Defective goods (improper quality) follow separate consumer rights and warranty rules (not limited to the 14-day exchange window): add a return reason class DEFECT with its own flow: inspection record, evidence photos, supplier claim link (purchase return in B6), warranty period fields on products. Specific remedies/timelines are rule parameters (not seeded).
- Policy vs law: company policy may be MORE generous than the legal floor, never less for eligible goods. The settings validator rejects a return window below the legal floor for legally returnable categories (floor comes from the rule pack), and the POS return flow refuses to deny an eligible return unless a documented legal exclusion applies (exclusion reason recorded). Receipt-less returns remain a company-policy decision with approval (B8), but the system looks up electronic receipts (fiscal receipt number, card, phone) first to avoid unnecessary refusals.
- Day counting: window = N days after the purchase date (purchase day excluded), computed in Asia/Baku business dates and respecting official non-working days only if the verified rule says so (parameter `count_calendar_days=true` by default).
- Refund timing and method parameters (e.g. days to refund, refund to original tender) as verified rule data; refund SLA tracked and reported (overdue refunds alert).
- Customer-facing return policy text (az) generated from the active rule + company policy, printable on receipts/website; version-controlled.

7) PERSONAL DATA PROTECTION (extends B2/B10/B11)
Reference (UNVERIFIED; Law "On Personal Data" No. 998-IIIQ of 11 May 2010 and Cabinet decrees on registration of personal-data information systems and on protection requirements): collection, processing and cross-border transfer of personal data require the data subject's written consent unless a legal exception applies; cross-border transfer is allowed where the recipient jurisdiction ensures equivalent protection or with consent; personal-data information systems generally must be registered with the authorized state body (certain categories exempt) — authority name and procedure are reported inconsistently → VERIFY; subjects have rights of access, correction, blocking, destruction; owners/processors must secure the data; administrative and criminal liability exists.
- Data inventory (record of processing): table `data_processing_register` (system/module, data categories, purpose, legal basis=consent/contract/legal obligation, subjects: customers/employees/suppliers' contacts, retention, recipients/processors, storage location/country, cross-border flag, security measures, owner). Pre-seed entries for CRM, loyalty, HR/payroll, POS receipts, audit logs, notification providers (all marked REVIEW_REQUIRED).
- Consent evidence: extend B11 consent_records with `form_version_id`, `consent_text_hash`, `capture_method` (paper_scan, e-signature, checkbox+OTP, in-app), `evidence_file_id`, `captured_by`, language, and separate purposes (loyalty, marketing per channel, cross-border transfer, profiling). WRITTEN-CONSENT support: signed paper scan upload or electronic confirmation with OTP (OTP provider NOT_CONFIGURED until chosen). Consent forms are versioned documents (az) managed by compliance.privacy.manage; changing text requires new consent where the rule says so.
- Employee data: HR consent/notice records for employees; contract-necessity vs consent basis recorded per data category (verified by counsel).
- Cross-border control: `transfer_register` of processors/hosts/providers (cloud, SMS, email, payment, analytics) with country, safeguards, consent coverage. Feature gate: enabling an integration or hosting region outside Azerbaijan requires a transfer-register entry marked VERIFIED, otherwise the integration cannot be activated in production. Data residency setting documents where primary DB and backups live; B14 backup jobs must respect it.
- Registration tracker: `personal_data_system_registration` (status NOT_ASSESSED / EXEMPT_VERIFIED / REGISTRATION_PENDING / REGISTERED, reference number, date, authority, evidence) — manual tracking, no auto-submission; compliance dashboard warns in production if status is NOT_ASSESSED.
- Subject rights workflow (extends B11 DSAR): access, correction, blocking, destruction requests with SLA parameters (rule data), identity verification step, outcome log; erasure respects retention conflicts (tax/accounting retention overrides: anonymize instead).
- Security requirements checklist mapped to controls already built (access control, audit, encryption, masking, backups) with evidence links; incident/breach register (detect, assess, notify decision, notes) — notification duties are rule data to be verified.
- Minimization defaults: collect name + phone only for loyalty; birth date/gender optional with explicit purpose; no national ID in CRM; HR sensitive data stays encrypted (B10).
- CCTV/biometric attendance and similar sensitive processing are OUT OF SCOPE; if later added they need a dedicated legal assessment (add as obligation template).
